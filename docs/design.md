## 一、项目概述

### 1.1 项目背景
随着大语言模型和人工智能智能体技术的发展，人工智能在文稿编写、文字修改、内容审核等办公场景中的应用越来越广泛。

然而，通用大语言模型在处理中文党政机关文稿时，仍然存在明显不足。

**第一，缺乏系统的机关文稿规范知识。**

通用模型虽然能够编写通知、报告、请示等文稿，但往往无法准确理解不同公文文种的适用范围、行文规则和结构要求，容易出现文种选择不当、行文关系错误、格式不规范等问题。

**第二，缺乏符合机关工作特点的表达能力。**

机关文稿在语言风格、逻辑结构、政治表述和政策术语等方面具有较强的专业性。

通用模型生成的内容容易出现口语化、空泛化、表达重复等问题，难以满足实际工作需要。

**第三，缺乏可靠的文稿审核机制。**

现有人工智能写作工具通常侧重于内容生成，而对文稿的规范性、完整性、一致性、语言准确性和事实可靠性缺少系统审核。

**第四，缺乏结构化、可复用的机关文稿知识。**

机关文稿编写涉及公文规范、常见文种、结构模板、政策术语、表达方式和公开优秀案例等大量专业知识。

这些知识往往分散在不同来源中，缺少面向 AI Agent 的统一组织和调用方式。

### 1.2 项目定位
`cn-official-doc-skills` 是一个基于 Agent Skills 开放规范构建的中文机关文稿智能体能力库。

项目通过结构化的规范知识、写作流程、审核规则、公开案例和表达语料，为人工智能智能体提供专业的中文机关文稿编写与审核能力。

**项目的核心目标不是开发一个新的人工智能聊天工具，而是让现有 AI Agent 具备更专业、更规范、更可靠的中文机关文稿处理能力。**

项目采用独立、可组合的 Skills 组织能力，尽可能降低对特定模型、智能体框架和商业平台的依赖。

Agent Skills 开放规范使用 `SKILL.md` 描述能力，并允许通过 `references/`、`scripts/` 和 `assets/` 等目录组织参考资料、执行脚本及辅助资源，适合作为本项目的基础。[GitHub](https://github.com/agentskills/agentskills)

### 1.3 目标用户
项目主要面向以下用户群体：

| 用户群体 | 主要使用场景 |
| --- | --- |
| 党政机关工作人员 | 公文起草、工作总结、通知编写、文字修改 |
| 事业单位工作人员 | 工作报告、汇报材料、实施方案编写 |
| 国有企业工作人员 | 正式文件、工作方案、总结报告编写 |
| 基层工作人员 | 基层工作材料、情况汇报、调研报告编写 |
| 机关文字工作者 | 文稿润色、逻辑优化、内容审核 |
| AI Agent 开发者 | 构建具有中文机关文稿处理能力的智能体 |
| 公文学习者 | 学习公文规范、文稿结构与机关语言表达 |

### 1.4 设计原则
项目遵循六项核心原则。

| 设计原则 | 说明 |
| --- | --- |
| 规范优先 | 公文规范和权威依据优先于模型自身生成习惯 |
| 中文强制 | 所有正式成稿必须使用中文，非允许的外语内容不得通过审核 |
| 事实可靠 | 不得编造政策、数据、文件依据及工作事实 |
| 能力模块化 | 不同文稿处理能力独立封装，可以组合使用 |
| 结果可验证 | 重要审核规则应具备可执行、可测试的验证方式 |
| 开源可扩展 | 支持社区补充公开案例、表达语料、文稿规则和审核能力 |

## 二、项目目标与边界

### 2.1 总体目标
构建一套**面向中文机关文稿的规范驱动型 AI Agent Skills 能力体系**，实现从文稿任务理解、规范匹配、内容编写到质量审核的标准化处理。

重点解决三个问题：

1. **能不能写：** 根据文稿类型、任务要求和已知事实，生成符合要求的中文机关文稿。
2. **写得是否规范：** 对文种、结构、语言、内容等进行规范约束。
3. **结果是否可靠：** 对事实依据、缺失信息、语言使用和规范问题进行审核，并输出可追溯的结果。

### 2.2 核心能力规划
项目规划五个核心能力方向。

| 能力模块 | 英文标识 | 核心职责 | 优先级 |
| --- | --- | --- | --- |
| 规范知识 | Standards | 公文规范、行文规则、文种知识 | P0 |
| 文稿编写 | Drafting | 根据任务要求起草中文机关文稿 | P0 |
| 文稿审核 | Review | 审核结构、语言、事实与规范问题 | P0 |
| 公开案例 | Corpus | 整理公开发布的典型文稿和案例 | P1 |
| 表达语料 | Lexicon | 规范术语、常用表达和语言优化参考 | P1 |

其中，**Standards 是整个项目的基础，Drafting 和 Review 是直接面向用户的核心能力。**

Corpus 和 Lexicon 是增强性知识模块，为文稿编写和审核提供辅助参考。

### 2.3 v0.1.0 版本范围
首个版本不追求覆盖所有机关文稿类型，也不追求构建复杂的 AI 应用平台。

v0.1.0 的重点是验证三个核心能力：

**规范驱动写作、严格审核和中文成稿约束。**

| 功能 | v0.1.0 |

| Agent Skills 标准结构 | 实现 |
| 公文规范知识库 | 实现基础内容 |
| 通知、报告、请示写作 | 实现 |
| 文稿结构审核 | 实现 |
| 文稿语言审核 | 实现 |
| 中文强制检测 | 实现 |
| 事实缺失和不确定内容检查 | 实现基础能力 |
| 审核结果结构化输出 | 实现 |
| 自动化测试 | 实现 |
| 大型公开案例库 | 暂缓 |
| 完整表达语料库 | 暂缓 |

这里需要特别说明：

项目本身是一套 Agent Skills 和辅助验证工具，使用者可以在支持 Skills 的智能体环境中调用其能力。

## 三、总体技术架构

### 3.1 架构设计
项目采用分层、模块化的设计方式。

\`\`\`mermaid
flowchart LR
    U[用户文稿任务] --> A[AI Agent 执行环境]
    A --> D[Drafting 文稿编写]
    A --> R[Review 文稿审核]
    D --> S[Standards 规范知识]
    R --> S
    D --> C[Corpus 公开案例]
    D --> L[Lexicon 表达语料]
    D --> V[Validators 确定性验证工具]
    R --> V
    D --> O[中文文稿及审核报告]
    R --> O
\`\`\`

说明：

- **AI Agent 执行环境：** 负责理解用户任务、调用 Skills、执行工具。
- **Standards：** 提供规范知识及规则依据。
- **Drafting：** 负责文稿起草、修改和优化。
- **Review：** 负责文稿审核和问题说明。
- **Corpus：** 提供公开案例参考。
- **Lexicon：** 提供专业表达和术语参考。
- **Validators：** 使用程序检查可以确定性验证的规则。
其中，Validators 并不作为独立的 AI Agent 存在，而是为 Skills 提供可执行的验证能力。

### 3.2 为什么不采用复杂的多智能体架构
项目早期不建议设计多个独立智能体分别负责写作、审核、政策研究和格式检查。

主要原因是：

**第一，项目定位是 Skills 能力库，而非智能体运行平台。**

不同使用者可能采用不同的 Agent 环境，不应要求所有用户采用固定的多智能体框架。

**第二，过度复杂的编排会增加使用成本。**

如果简单编写一篇通知就需要执行多个模型调用任务，会增加延迟和 Token 消耗。

**第三，Skills 应当具有独立性。**

用户可以只调用写作能力，也可以只调用审核能力。

因此，初期建议采用：

**独立 Skills + 共享规范 + 确定性验证工具**

后续再根据实际使用需求扩展复杂工作流。

这里有一个重要的设计决定：

**Standards、Corpus 和 Lexicon 不需要全部设计成独立 Skill。**

它们首先是知识资源库。

真正直接面向用户任务的 Skills 应当是 Drafting、Review 等能力。

这样能够避免项目出现几十个职责重复、调用条件不清晰的 Skills。

### 4.2 跨目录资源加载约定
标准 Agent Skills 要求每个 Skill 至少包含一个 `SKILL.md`，可以包含自身的参考资料和脚本。[GitHub](https://github.com/agentskills/agentskills/blob/main/docs/home.mdx)

但不同 Agent 运行环境对 Skill 根目录以外文件的读取能力可能不同。

因此，项目需要明确两个概念：

**源代码结构**和**发布结构**。

开发仓库可以使用统一的 `standards/`、`lexicon/` 等共享资源目录。

发布时则应当根据需要，把对应的规范知识复制或打包至 Skill 内部，形成自包含的 Skill 包。

这样能够避免某些智能体环境只安装单个 Skill 时，出现无法读取外部规范文件的问题。

## 五、Standards：规范知识体系

### 5.1 模块定位
Standards 是项目中最重要的基础模块。

它决定文稿编写和审核过程中，人工智能能够依据哪些规范作出判断。

主要职责包括：

- 管理正式公文处理规范。
- 管理不同文种的适用范围。
- 提供公文行文规则。
- 管理文稿结构要求。
- 管理规范来源和有效性信息。
- 为写作和审核能力提供统一依据。

### 5.2 规范来源
规范知识应当优先来源于公开、权威的正式文件。

初期建议以以下文件作为基础依据：

| 规范名称 | 用途 |
| --- | --- |
| 《党政机关公文处理工作条例》 | 公文文种、行文规则、公文办理等 |
| 《党政机关公文格式》GB/T 9704—2012 | 正式公文版式、格式要求 |
| 其他现行有效的权威规范文件 | 对具体文稿场景补充约束 |

《党政机关公文处理工作条例》明确了15种主要公文文种；GB/T 9704—2012目前在全国标准信息公共服务平台显示为现行推荐性国家标准。[中国政府网](https://big5.www.gov.cn/gate/big5/www.gov.cn/zhengce/2013-02/22/content_2640088.htm)

需要注意：

**不是所有机关工作材料都属于法定公文。**

例如，工作总结、领导讲话稿、调研材料和经验交流材料，不能简单地按照法定公文文种要求进行审核。

项目必须区分：

1. 法定公文。
2. 一般机关事务文稿。
3. 具有特定用途的工作材料。
不同类别适用不同的规则体系。

### 5.3 规范结构化设计
规范内容不能只是把条例原文复制到 Markdown 文件中。

应当将规范转化为便于 AI 理解、检索和验证的结构化知识。

例如：

```
id: DOC_TYPE_REQUEST
name: 请示
category: statutory_document

definition: 向上级机关请求指示、批准的公文。

applicable_scenarios:
  - 请求上级机关作出指示
  - 请求上级机关批准事项

writing_requirements:
  - 明确请示事项
  - 说明请示理由
  - 提出明确请求
  - 原则上坚持一文一事

validation_rules:
  - 检查请示事项是否明确
  - 检查是否存在明显的多事项混写
  - 检查是否误将请示写为报告

source:
  title: 党政机关公文处理工作条例
  article: 第八条、第十五条
  authority: 中共中央办公厅、国务院办公厅
```

其中，结构化字段可以辅助 Agent 完成文种识别和规则匹配。

但是，不同审核要求的自动化能力有所区别。

例如：

- 是否存在必需的标题：适合程序检测。
- 是否存在多个相互独立的请示事项：需要语义分析和人工复核。
- 请示对象是否符合行文关系：通常需要用户提供组织关系背景。
不能将这些问题都错误地归类为简单的程序判断。

### 5.4 规范优先级
对于规范冲突，建议采用以下基本原则：

**现行有效的上位规范优先于下位规范；正式规范优先于经验性写作建议。**

项目内部再区分三个等级：

| 等级类型 | 处理方式 |
| --- | --- |
| 强制规则 | 必须执行的规范要求，不满足则报告违规 |
| 条件规则 | 特定文种或场景适用，根据条件触发 |
| 建议规则 | 风格、结构、表达方面的建议，提供优化建议 |

需要特别注意：

项目自身设置的“中文强制成稿”属于**项目质量门禁规则**，不应错误解释为国家公文法规要求所有场景禁止外文字符。

## 六、Drafting：机关文稿编写能力

### 6.1 模块定位
Drafting 负责根据用户的工作任务和已知信息，生成符合要求的中文机关文稿。

它不是简单地调用一次大语言模型生成正文。

而是按照预先定义的写作流程完成文稿编制。

### 6.2 支持的文稿类型
v0.1.0 首先支持：

| 文稿类型 | 示例场景 |
| --- | --- |
| 通知 | 工作安排、会议组织、事项通知 |
| 报告 | 工作情况报告、专项工作报告 |
| 请示 | 经费申请、事项审批、工作请求 |

选择这三种文稿作为首批支持范围，主要是因为它们较为常见，同时在用途和结构上具有一定代表性。

后续可以扩展：

- 函、通报、批复。
- 工作总结、工作计划。
- 工作方案、实施方案。
- 调研报告、经验交流材料。
- 领导讲话稿、汇报提纲。

### 6.3 输入信息设计
Drafting 应当尽可能识别以下输入信息：

| 输入字段 | 说明 | 是否必需 |
| --- | --- | --- |
| 文稿类型 | 通知、报告、请示等 | 是，可由 Agent 推断并确认 |
| 写作目的 | 希望解决什么问题 | 是 |
| 主要内容 | 用户提供的事实和工作事项 | 是 |
| 发文主体 | 文稿的起草或发文单位 | 视场景而定 |
| 接收对象 | 上级、下级或其他单位 | 视场景而定 |
| 时间范围 | 具体时间、工作周期 | 视场景而定 |
| 篇幅要求 | 字数、段落数量等 | 否 |
| 特殊要求 | 风格、重点、结构等 | 否 |

对于缺失信息，不能一律自行补全。

例如：

用户要求编写一份关于某项工作的情况报告，但未提供工作成果数据。

Agent 可以根据已知事实组织报告结构，但不能虚构工作完成率、资金投入和具体成效。

### 6.4 写作工作流
\`\`\`mermaid
flowchart TD
    A[接收用户任务] --> B[识别文稿类型]
    B --> C[匹配适用规范]
    C --> D[提取事实与约束]
    D --> E{关键信息是否充分}
    E -- 否 --> F[请求补充必要信息]
    F --> D
    E -- 是 --> G[构建文稿结构]
    G --> H[生成中文初稿]
    H --> I[调用审核与验证]
    I --> J{是否通过}
    J -- 否 --> K[根据问题修改]
    K --> I
    J -- 是 --> L[交付最终文稿]
\`\`\`

实际执行中，不必要求用户补齐所有字段。

只有当缺失的信息直接影响文稿正确性，且无法通过明确标注待补充内容处理时，才需要向用户追问。

### 6.5 写作质量要求
编写能力需要满足以下要求。

**结构规范。**

根据文稿类型确定相应结构，不得机械套用与文种不符的模板。

**逻辑清晰。**

做到主题明确、层次合理、前后衔接自然。

**表达正式。**

保持符合机关工作场景的语言风格，避免明显口语化和不适当的网络表达。

**事实可靠。**

所有具体事实、数据、政策依据应当有来源或明确由用户提供。

**内容完整。**

不能为了满足形式上的简洁而遗漏用户明确要求的重要事项。

**中文成稿。**

正式文稿执行项目统一的中文语言规则。

## 七、Review：文稿质量审核能力

### 7.1 模块定位
Review 是项目的第二个核心执行能力。

它不仅负责发现文字错误，还应针对机关文稿的特点进行专业审核。

建议设计为六个审核维度。

| 审核维度 | 主要内容 |
| --- | --- |
| 文种规范 | 文稿类型是否适当，是否符合适用场景 |
| 结构完整性 | 标题、正文、层次和必要要素是否完整 |
| 语言规范 | 用词、语法、标点、书面表达是否合理 |
| 内容逻辑 | 是否存在矛盾、重复、前后不一致 |
| 事实可靠性 | 是否存在无依据的数据、政策、事实性表述 |
| 中文语言合规 | 是否包含不允许出现的外文内容 |

### 7.2 审核规则分类
为了提高审核结果的可靠性，应当区分两类审核规则。

#### 第一类：确定性审核
由程序执行，规则明确、结果可以复现。

例如：

- 检查是否包含未获允许的英文字母。
- 检查标题是否缺失。
- 检查明显的非法字符。
- 检查结构化输入中的必需字段。
- 检查 Skill 文件是否符合规范。
此类审核适合使用 Python 实现。

#### 第二类：语义审核
由 AI Agent 结合规范知识判断。

例如：

- 文种选择是否合理。
- 是否存在明显的逻辑矛盾。
- 行文语气是否适当。
- 机关语言是否规范。
- 内容是否空泛。
- 请示事项是否明确。
语义审核应当提供判断理由，尽量关联具体规则，不得把不确定结论伪装为确定事实。

### 7.3 问题等级
建议定义四个等级：

| 等级 | 标识 | 说明 |
| --- | --- | --- |
| 严重 | ERROR | 违反强制规则、明显事实错误等 |
| 警告 | WARNING | 可能影响文稿规范性的问题 |
| 建议 | SUGGESTION | 语言、结构、风格优化建议 |
| 待核实 | VERIFY | 需要外部事实或用户补充信息 |

其中，事实尚未核实与事实已被证伪必须严格区分。

### 7.4 审核输出示例
假设用户提交以下文字：

> 关于开展2026年度工作总结的通知
> 请各单位于下周五前提交年度总结，具体材料包括工作成果、存在问题以及Next Steps。
审核结果可表示为：

```
{
  "document_type": "通知",
  "status": "failed",
  "issues": [
    {
      "rule_id": "LANG-001",
      "severity": "ERROR",
      "category": "language",
      "text": "Next Steps",
      "message": "正式中文文稿中包含未获允许的英文表达。",
      "suggestion": "后续工作计划"
    },
    {
      "rule_id": "FACT-001",
      "severity": "VERIFY",
      "category": "fact",
      "text": "下周五",
      "message": "提交截止时间使用相对日期，需核实具体日期。",
      "suggestion": "明确为具体年月日。"
    }
  ]
}
```

这里的 `status` 表示机器审核状态，不代表文稿已经通过人工审批。

## 八、中文强制规则设计
这一部分需要作为项目的核心设计要求，而不是普通的写作建议。

### 8.1 基本要求
项目规定：

**所有正式交付的机关文稿，必须使用中文编写。除明确允许的特殊表达外，不得包含其他语言内容。**

该要求适用于：

- 文稿初稿生成。
- 文稿修改。
- 文稿润色。
- 文稿审核。
- 最终交付。

### 8.2 语言策略
建议定义以下核心规则。

| 规则编号 | 规则名称 | 要求 |
| --- | --- | --- |
| LANG-001 | 中文成稿 | 正式文稿必须使用中文 |
| LANG-002 | 外语检测 | 自动检测未获允许的外文字符与表达 |
| LANG-003 | 例外管理 | 特殊术语必须符合白名单要求 |
| LANG-004 | 禁止绕过 | 不能以用户未要求审核为理由绕过语言校验 |
| LANG-005 | 交付门禁 | 未通过语言校验的正式文稿不得交付 |

### 8.3 白名单机制
实际机关文稿可能存在少量需要保留的特殊表达。

例如：

- `GDP`
- `WTO`
- `ISO`
- `5G`
但白名单不能无限扩大。

建议配置为：

```
language_policy:
  primary_language: zh-CN

  strict_mode: true

  allow_foreign_text: false

  allowed_terms:
    - GDP
    - WTO
    - ISO
    - 5G

  validation:
    enabled: true
    block_on_error: true
```

这里还需要明确三个细节。

第一，白名单中的术语仅在确有必要时允许保留，不代表建议优先使用缩写。

第二，白名单应当支持记录中文名称和使用条件。

第三，配置中的默认白名单只是初步示例，项目正式发布前应当逐项审查。

### 8.4 机器检测实现
建议使用 Python 构建独立语言检查器。

核心程序：

`validate_language.py`

检测流程包括：

1. 提取待审核文稿正文。
2. 识别外语字符及连续表达。
3. 排除符合规则的允许术语。
4. 生成违规位置和原因。
5. 返回机器可识别的审核结果。
6. 根据审核结果决定是否允许交付。
需要特别注意：

**不能仅仅通过检测 ASCII 英文字母来判断所有外语违规情况。**

例如，其他文字系统中的字符并不属于 ASCII 范围。

因此，程序应当采用 Unicode 字符分类及文字系统识别，同时结合白名单处理允许出现的专有表达。

此外，Markdown、JSON、代码字段中的英文标识不应与正式文稿正文混为一谈。

项目需要在检测前确定受检文本范围。

## 九、Corpus：公开案例库

### 9.1 模块定位
Corpus 为智能体提供具有参考价值的公开机关文稿案例。

其目的不是简单堆积大量文稿，而是形成可以根据文种、主题和结构进行参考的案例资源。

### 9.2 数据来源
优先考虑：

- 中国政府网公开文件。
- 各级政府官方网站公开文件。
- 公开发布的工作报告。
- 合法公开且允许相应使用的其他文稿资料。
案例应当记录原始链接、发布时间、发布机构和来源。

不应收集内部未公开文件、涉密材料或者个人隐私信息。

### 9.3 案例组织结构
示例：

```
id: CASE-0001

title: 某项工作情况报告

document_type: 报告

category: 工作情况

source:
  organization: 示例单位
  url: https://example.com
  published_at: 2026-01-01

features:
  - 工作背景
  - 工作开展情况
  - 存在问题
  - 下一步计划

quality_status: reviewed
```

上述内容仅展示数据结构，不代表真实案例。

### 9.4 案例版权要求
公开发布不等于可以不受限制地复制、修改和重新分发。

因此，项目需要建立来源许可审核机制。

对于不宜完整转载的案例，可以只保存：

- 标题。
- 来源链接。
- 文稿类型。
- 结构特征。
- 基于事实整理的简要分析。
**v0.1.0 不建设大型案例库。**

初期只需要少量经过核实、许可合规的示例，帮助测试文稿编写和审核能力即可。

## 十、Lexicon：机关文稿表达语料

### 10.1 模块定位
Lexicon 为人工智能提供规范术语、常见书面表达、语义辨析和文稿表达优化参考。

其目标是改善模型生成内容中常见的：

- 口语化。
- 空泛化。
- 用词不准确。
- 重复表达。
- 文风不符合使用场景等问题。

### 10.2 语料分类
建议设计以下类别。

| 分类 | 内容 |
| --- | --- |
| 规范术语 | 常见机关工作专业术语 |
| 结构表达 | 引出背景、说明情况、提出要求等 |
| 工作表达 | 部署、推进、落实、总结等 |
| 问题表达 | 分析不足、指出问题、阐明原因 |
| 逻辑衔接 | 因果、递进、并列、转折等 |
| 易错用语 | 容易混淆或误用的词语 |

### 10.3 数据组织
例如：

```
id: EXP-0001

category: work_arrangement

expression: 统筹推进

meaning: 强调对多项工作进行统一协调和推动。

appropriate_contexts:
  - 多项任务协同实施
  - 多部门工作协调

inappropriate_contexts:
  - 简单的单项事务
  - 无须统筹协调的具体操作
```

Lexicon 不应被设计成“套话生成库”。

重点是让 Agent 理解表达的适用条件，而不是鼓励堆砌固定句式。

## 十一、Skills 执行与协作机制

### 11.1 Skill 定义
每个 Skill 都采用 Agent Skills 标准格式。

以编写能力为例：

```
---
name: official-document-drafting
description: 用于编写、修改和优化中文党政机关公文及常见机关工作材料，包括通知、报告、请示等。执行规范匹配、事实约束和中文成稿检查。
---
```

正文部分负责定义：

- 适用任务。
- 执行步骤。
- 所需规范。
- 输出要求。
- 审核约束。
- 异常处理。

### 11.2 核心执行流程
用户提出写作任务后，Agent 首先判断文稿类型并加载适用规范。

随后根据用户提供的信息组织内容，完成中文文稿初稿。

初稿形成后，执行结构、语言和事实相关审核。

对于发现的问题，Agent 可以进行修改。

但是：

**不能通过修改文字的方式掩盖缺失的事实，也不能为了让审核通过而编造信息。**

### 11.3 写作与审核的关系
建议采用以下规则：

**直接审核任务：**

调用 Review，返回审核意见。

**直接写作任务：**

调用 Drafting，在交付前执行必要审核。

**修改已有文稿：**

根据用户修改要求处理内容，并重新执行相关检查。

在支持程序执行的环境中，语言检查应当调用确定性验证脚本，而不应仅要求模型自行判断。

对于无法执行脚本的环境，应当明确其审核能力受到限制，不能宣称已完成机器验证。

## 十二、技术选型

### 12.1 技术栈
v0.1.0 建议采用尽可能轻量的技术方案。

| 技术 | 用途 | 是否必需 |
| --- | --- | --- |
| Markdown | Skills 指令、规范文档 | 必需 |
| YAML | 结构化规则配置 | 必需 |
| Python 3.11+ | 校验脚本、自动化测试 | 必需 |
| Pytest | 单元测试 | 必需 |
| GitHub Actions | 持续集成 | 推荐 |
| JSON | 审核结果交换格式 | 推荐 |
| Git | 版本管理 | 必需 |

此阶段不需要：

- 数据库。
- Redis。
- Docker。
- Web 前端。
- Java 后端。
- 向量数据库。
- 自建大语言模型服务。
这里需要区分**项目运行依赖**与**实际生成文稿的模型依赖**。

项目仓库自身可以无服务器运行，但文稿的语义理解和生成仍需要用户所使用的 AI Agent 具备相应模型能力。

### 12.2 Python 的使用范围
Python 不承担文稿生成任务。

其职责主要包括：

- 语言规则检测。
- 结构化规则校验。
- Skill 格式检查。
- 测试执行。
- 检查结果生成。
这样能够让大语言模型处理语义任务，让程序负责确定性的规则任务。

### 12.3 为什么不立即引入 LangChain 等框架
当前项目不是完整的 AI 应用编排系统。

如果只是为了编写几个 Skills 而引入复杂 Agent 框架，会增加维护成本，也会降低项目对不同运行环境的兼容性。

因此，建议 v0.1.0 不依赖特定 Agent 框架。

## 十三、质量保证与测试设计

### 13.1 测试目标
项目的质量保证应当包括两个层面：

**第一，程序规则正确。**

例如，语言检测脚本是否能够稳定识别违规内容。

**第二，Skills 执行有效。**

例如，Agent 是否能够根据规范选择正确文种、编写合适的内容并发现明显错误。

两者需要分别测试。

### 13.2 确定性测试
使用 Pytest 对脚本进行自动化测试。

重点包括：

| 测试场景 | 预期结果 |
| --- | --- |
| 完整中文正文 | 通过 |
| 包含普通英文单词 | 拒绝 |
| 包含允许的缩写 | 按白名单规则处理 |
| 包含未允许的外语文字 | 拒绝 |
| 包含 Markdown 代码字段 | 按受检范围进行判断 |
| 缺少文稿正文 | 返回明确错误 |
| 配置文件格式错误 | 返回配置错误 |
| Skill 缺少必要元数据 | 校验失败 |

### 13.3 Skills 行为测试
对写作和审核能力建立测试样例。

例如：

**测试任务：**

> 请帮我写一份向上级机关申请开展某项专项工作的请示。
预期行为：

- 正确识别请示文种。
- 对缺失的关键事实进行处理。
- 不虚构申请事项及资金数额。
- 使用符合请示用途的结构。
- 输出中文文稿。
- 在具备执行条件时完成语言校验。

### 13.4 质量门禁
建议把项目测试划分为三个等级：

| 等级 | 内容 | 是否阻止合并 |
| --- | --- | --- |
| P0 | Skill 格式、程序错误、中文强制规则 | 是 |
| P1 | 规范引用、核心场景测试 | 是 |
| P2 | 表达质量、案例丰富度等 | 否 |

对于模型输出质量评测，需要避免把单次模型测试结果误认为稳定能力。

建议后续引入：

- 固定测试任务集。
- 多次运行结果比较。
- 人工审核基准。
- 错误类型统计。

## 十四、安全与合规设计
项目涉及正式机关文稿，需要比一般的文本生成项目更关注事实、数据和规范来源。

### 14.1 事实约束
严禁编造：

- 政策文件名称和文号。
- 工作完成数据。
- 政府部门决策。
- 资金数额。
- 统计指标。
- 未提供的具体工作成果。
对于无法核实的内容，应当明确标注待核实，或者请求用户补充。

### 14.2 数据安全
项目不得默认要求用户上传内部文件至第三方平台。

Skills 本身也不应设计为自动收集文稿内容并上传至项目维护者服务器。

如果用户使用的是云端模型，其数据处理方式还取决于具体模型服务和运行环境。

因此，项目应当在文档中说明相关隐私与使用边界。

### 14.3 规范真实性
禁止将未经核实的网络经验文章包装成国家规范。

每项正式规范建议记录：

- 名称。
- 发布主体。
- 发布时间。
- 施行时间。
- 效力状态。
- 来源链接。
- 最后核验时间。
对于无法确认的规范，不应直接作为强制审核依据。

### 14.4 模型输出边界
项目不应宣称生成的文稿已经获得正式机关审批。

最终文件仍应由具有相应职责的人员审查、签发。

## 十五、项目实施计划

### 15.1 第一阶段：基础工程
目标是建立规范的 GitHub 仓库。

主要工作：

1. 创建项目目录结构。
2. 编写 README。
3. 确定开源协议。
4. 设计 Skills 文件规范。
5. 创建 Python 测试环境。
6. 配置 GitHub Actions。
**阶段成果：** 仓库结构完整，能够自动检查 Skill 元数据及基础程序。

### 15.2 第二阶段：规范知识库
目标是建立支持核心文种的结构化规范。

主要工作：

1. 整理《党政机关公文处理工作条例》相关要求。
2. 建立规范来源索引。
3. 设计文种知识结构。
4. 完成通知、报告、请示的基础规则。
5. 设计规范规则编号。
6. 编写对应测试案例。
**阶段成果：** 初步形成规范驱动的知识基础。

### 15.3 第三阶段：文稿编写 Skill
目标是实现 Drafting 核心能力。

主要工作：

1. 编写 `SKILL.md`。
2. 设计文稿编写流程。
3. 制定事实约束规则。
4. 创建三类文稿模板。
5. 实现规范知识引用。
6. 编写测试任务。
**阶段成果：** 能够处理通知、报告、请示的基本编写需求。

### 15.4 第四阶段：审核 Skill
目标是实现 Review 核心能力。

主要工作：

1. 建立审核规则体系。
2. 定义审核问题等级。
3. 实现语言检测脚本。
4. 实现基础结构检测。
5. 制定审核报告格式。
6. 对典型错误样例进行测试。
**阶段成果：** 可以对常见机关文稿进行结构化审核，并执行中文语言校验。

### 15.5 第五阶段：集成验证与发布
目标是完成 v0.1.0。

主要工作：

1. 验证写作与审核流程。
2. 检查 Skills 在目标 Agent 环境中的实际执行情况。
3. 完善用户使用说明。
4. 完善测试样例。
5. 编写更新日志。
6. 发布 GitHub Release。
**阶段成果：** 可安装、可使用、可验证的首个公开版本。

## 十八、开源项目治理

### 18.1 开源协议
初步建议考虑 MIT 或 Apache-2.0。

其中，Apache-2.0 更适合希望明确专利授权与贡献边界的代码项目。

但需要强调：

项目采用什么开源协议，不会自动赋予项目对第三方公文案例和资料的再分发权。

因此，代码许可与第三方内容使用许可必须分别管理。

### 18.2 贡献规范
社区可以参与：

- 修正错误的规范知识。
- 补充文种规则。
- 优化 Skills 指令。
- 增加测试样例。
- 改进校验脚本。
- 提交合规的公开案例。
- 改进表达语料。
对于规范类贡献，应要求附上权威来源。

不接受无法核实、明显错误或者来源不合规的规范资料。

### 18.3 文档语言
项目的用户文档、规范说明、案例分析、贡献指南和正式示例内容原则上统一使用简体中文。

代码标识符、标准文件名、技术协议名称以及必要的机器可读字段允许采用符合技术规范的英文命名。

正式机关文稿仍独立执行更严格的中文成稿门禁。

## 十九、主要风险及应对方案
| 风险 | 影响 | 应对方案 |
| --- | --- | --- |
| 规范知识不准确 | 生成或审核结果错误 | 建立权威来源和人工核验流程 |
| Skills 过度依赖模型 | 不同模型表现差异明显 | 使用确定性脚本承接可程序化的规则 |
| 审核规则过于僵化 | 错误拦截合理表达 | 区分强制规则、条件规则和建议规则 |
| 文稿内容空泛 | 实际工作可用性降低 | 建立事实约束、写作结构和质量评测 |
| 文稿类型混淆 | 错误应用公文规范 | 区分法定公文与一般机关工作材料 |
| 案例版权问题 | 影响开源发布 | 建立来源及许可审核机制 |
| Skills 兼容性不足 | 无法在部分 Agent 中正常使用 | 使用标准结构并验证发布包 |
| 功能不断膨胀 | 项目难以按期完成 | 明确 v0.1.0 的功能边界 |

## 二十、项目的核心价值与长期方向
我认为，`cn-official-doc-skills` 最值得持续投入的，不是不断添加文稿模板，而是建立三个能够形成长期价值的基础能力。

### 20.1 可追溯的机关文稿规范体系
普通提示词可以告诉模型“请使用正式公文语言”。

但本项目需要更进一步，让模型知道：

- 某项要求依据什么规范。
- 对哪些文稿类型适用。
- 哪些要求必须遵守。
- 哪些只是写作建议。
- 违反规则应当如何修改。
这是项目专业性的重要来源。

### 20.2 可执行的质量审核机制
项目不应当只输出“这篇文章整体不错，但还需要进一步优化”这类缺少依据的意见。

而应努力做到：

**指出具体问题、解释问题原因、关联审核依据、给出修改建议，并在可执行场景中验证修改结果。**

尤其是中文强制规则、结构完整性等，可以逐步通过程序实现稳定检查。

### 20.3 可积累的中文机关表达知识
在未来版本中，通过整理规范术语、典型结构、公开案例和高质量表达，建立一套具有持续维护价值的中文机关文稿知识资源。

但这个资源库必须以规范、准确、可追溯为基础，而不是单纯追求语料数量。

## 我的进一步建议
针对这个项目，我认为还有三个关键问题需要在正式编码前明确。

**第一，不要把项目做成公文模板大全。**

GitHub 上单纯收集 Markdown 模板、提示词和写作范例的项目，技术门槛并不高。

`cn-official-doc-skills` 应该形成区别：**规范是基础、Skills 是执行方式、审核是质量保障。**

这比单纯提供几百种写作模板更有长期价值。

**第二，Standards 是最值得认真建设的模块。**

如果底层规范错误，即使模型生成能力再强，也会产生错误结果。

因此，最初应该优先完成规范分类、来源管理、规则结构和适用范围设计，然后再完善 Drafting。

**第三，必须让 Review 真正发挥作用。**

如果写作结果不经过必要审核，项目就容易退化成一个普通的写作提示词。

建议把“写作—审核—修正—验证”作为项目默认工作流，并且从第一个版本开始落实中文语言强制检查。
