# 版本与发布流程

项目版本遵循语义化版本，并使用更新日志中的“未发布”区域记录开发中的变化。

## 版本选择

- 修正错别字、来源定位或元数据，且不改变既有能力含义：增加修订号，例如 `0.1.0` → `0.1.1`。
- 增加向后兼容的文种、规则或 Skill 能力：增加次版本号，例如 `0.1.0` → `0.2.0`。
- 产生不兼容的清单、规则数据结构或调用方式变化：明确迁移影响，并按语义化版本选择版本号。`0.x` 阶段也不得静默引入破坏性变化。

## 开发阶段

1. 在 `CHANGELOG.md` 的“未发布”区域记录重要变化。
2. 新来源先登记身份、效力、原始链接、许可边界和核验日期。
3. Agent 对照原文后，规则最高只能进入 `source_checked`；项目维护者复核后才能进入 `human_approved`。
4. 为直接影响 Skill 行为的规则添加结构化行为样例。
5. 运行开发门禁：

   ```bash
   python -m pytest
   python scripts/validate_repository.py
   ```

开发门禁允许尚待人工复核的候选规则存在。

## 发布阶段

1. 完成来源核验、人工签核、行为测试和目标 Agent 环境验收。
2. 仅将通过全部门禁的规则改为 `active`，并同步来源与测试覆盖状态。
3. 同步更新 `pyproject.toml`、`plugin.json` 和 `.codex-plugin/plugin.json` 的版本号。
4. 将更新日志中的“未发布”内容归入带日期的版本条目，并更新版本比较链接。
5. 运行严格发布门禁：

   ```bash
   python -m pytest
   python scripts/validate_repository.py --release
   ```

6. 建立版本验收记录，确认安装包只包含预期文件且可在目标环境真实安装。
7. 创建 `vX.Y.Z` Git 标签和 GitHub Release。

严格发布门禁要求全部正式规则均为 `active`、全部来源均可用，并验证各插件清单与项目版本一致。不得为了通过门禁而跳过人工复核。
