# Standards 规范知识体系设计

## 1. 文档目的

本文档定义 Standards 模块的组织方式、来源管理、规则结构和审核流程。

本阶段只建立知识治理框架，不直接录入尚未取得权威原文的公文规范。任何正式规则都必须能够追溯到用户提供或项目核验过的权威材料。

## 2. 模块边界

Standards 负责：

- 登记规范名称、发布主体、效力状态和权威来源；
- 区分法定公文、一般机关事务文稿和特定用途工作材料；
- 将规范原文转化为结构化规则；
- 记录规则的适用条件、强制等级和来源条款；
- 为 Drafting、Review 和确定性校验程序提供统一依据；
- 跟踪规范的复核、变更、替代和失效。

Standards 不负责：

- 代替发文机关判断具体组织隶属关系和职权范围；
- 将经验文章、培训讲义或个人写作习惯包装成正式规范；
- 推断用户没有提供的内部制度；
- 保存涉密、敏感或未经授权的内部文件；
- 自动取得第三方材料的再分发权。

## 3. 知识分层

### 3.1 来源层

记录规范原文及其元数据。来源优先级如下：

1. 中共中央、国务院及其办公厅公开发布的正式文件；
2. 国家标准化行政主管部门公开的国家标准；
3. 其他中央和国家机关公开发布且在其职责范围内适用的制度；
4. 地方党委、政府及其办公厅公开发布的现行制度；
5. 经授权使用的单位内部制度。

新闻报道、政策解读、培训资料和经验文章只能作为线索或辅助说明，不能单独成为强制规则依据。

### 3.2 规则层

规则层保存从权威材料中提取的结构化要求，包括：

- 文种定义和适用范围；
- 行文关系和行文规则；
- 文稿组成要素；
- 起草、审核和签发要求；
- 版式、标点和数字用法；
- 项目自身的质量门禁。

### 3.3 能力层

Drafting 和 Review 只能引用已经完成来源核验并处于启用状态的规则。候选规则、待复核规则和已失效规则不得作为确定性结论直接交付给用户。

## 4. 来源记录模型

每份来源至少记录以下字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 仓库内唯一来源编号 |
| `title` | 文件或标准正式名称 |
| `document_number` | 发文字号或标准号 |
| `authority` | 发布或主管主体 |
| `source_type` | 条例、国家标准、地方制度、内部制度等 |
| `issued_at` | 发布日期 |
| `effective_at` | 施行日期 |
| `status` | 现行、废止、被替代、待核验等 |
| `official_url` | 权威来源地址 |
| `retrieved_at` | 最后访问或核验日期 |
| `import_status` | 待导入、已接收、已提取、已复核 |
| `redistribution` | 是否允许在开源仓库保存全文 |
| `notes` | 适用范围、版权或其他说明 |

来源记录不能仅凭文件名判断真实性。导入时应同时核对正文标题、发布主体、文号、日期和网页来源。

## 5. 规则记录模型

每条规则建议包含以下字段：

```yaml
id: DOC-TYPE-REQUEST-001
title: 待从权威原文提取
category: document_type
level: mandatory
applies_to:
  document_types: []
  organizations: []
conditions: []
requirement: null
validation:
  mode: semantic
  deterministic_checks: []
source_refs:
  - source_id: null
    locator: null
    evidence: null
review:
  status: draft
  reviewed_by: null
  reviewed_at: null
```

示例中的内容只是字段结构，不代表任何已确认的公文规则。

### 5.1 规则等级

- `mandatory`：来源明确的强制要求；
- `conditional`：只有满足特定文种、组织关系或业务条件时适用；
- `recommended`：结构、表达和可读性方面的建议；
- `project_gate`：项目自行设定的质量门禁，不得冒充国家规范。

### 5.2 验证方式

- `deterministic`：可以由程序稳定判断；
- `semantic`：需要 Agent 结合语义和上下文判断；
- `context_required`：必须由用户提供组织关系、事实或业务背景；
- `human_review`：必须由具有相应职责的人员确认。

同一规则可以同时包含多种验证方式。

## 6. 规则编号

编号表达规则所属领域，不表达规范效力高低：

| 前缀 | 领域 |
| --- | --- |
| `DOC-TYPE` | 文种定义与适用范围 |
| `WRITING` | 起草与内容要求 |
| `ROUTING` | 行文关系与报送规则 |
| `FORMAT` | 公文格式与版式 |
| `PUNCT` | 标点符号 |
| `NUMBER` | 数字用法 |
| `LANG` | 项目语言门禁 |
| `FACT` | 项目事实可靠性门禁 |
| `REG` | 《党政机关公文处理工作条例》逐条覆盖记录 |

规则编号一经发布不重复使用。规则被替代时保留旧记录，并通过 `superseded_by` 指向新规则。

## 7. 来源导入流程

```mermaid
flowchart LR
    A[登记候选来源] --> B[用户提供权威原文]
    B --> C[核对标题、主体、文号与日期]
    C --> D[确认效力与许可边界]
    D --> E[逐条提取候选规则]
    E --> F[标注适用条件和来源位置]
    F --> G[人工复核]
    G --> H[启用规则]
```

如果原文缺失、来源不明、效力状态无法确认或条款存在歧义，流程停留在复核前，不得将相关内容标记为启用规则。

## 8. 首批建设范围

v0.1.0 先处理：

1. 通知、报告、请示的文种定义和适用范围；
2. 与上述文种直接相关的行文规则；
3. 公文通用组成要素；
4. 起草与审核的一般要求；
5. 公文基础格式；
6. 标点符号和数字用法；
7. 项目的中文成稿与事实可靠性门禁。

暂不处理：

- 涉密公文的具体技术和管理流程；
- 电子公文归档；
- 印刷设备、物理载体和专业排版实现；
- 所有十五种法定公文的完整规则；
- 一般工作总结、讲话稿和调研材料的详细规范；
- 未经授权的单位内部制度。

## 9. 启用标准

一条规则只有同时满足以下条件才能进入正式能力：

- 权威原文已经取得；
- 文件身份与效力状态已经核验；
- 规则文字没有超出原文含义；
- 适用对象和触发条件明确；
- 来源能够定位到具体条、款、项或标准章节；
- 强制规则与项目建议明确区分；
- 至少完成一次人工复核；
- 必要的正例、反例或测试场景已经建立。

### 9.1 复核状态

来源对照与人工签核必须分开记录：

- `extracted`：已经从原文提取，尚未完成逐条来源对照；
- `source_checked`：已经逐条对照原文，条款范围、摘要含义和定位均通过检查；
- `human_approved`：已经由项目维护者或具备相应职责的复核人员确认；
- `active`：人工确认、测试和覆盖门禁均通过，可以被正式能力使用。

Agent 完成原文对照只能进入 `source_checked`，不得代替人工复核并直接标记为 `human_approved` 或 `active`。

## 10. 变更管理

- 来源文件修订、废止或被替代时，重新评估全部引用规则；
- 规则内容变化应记录在更新日志中；
- 破坏现有规则数据结构的变化按照版本规则升级；
- 仅修正引用位置、错别字或元数据时，可以作为修订版本发布；
- 不得静默修改已经对外发布的规则含义。
