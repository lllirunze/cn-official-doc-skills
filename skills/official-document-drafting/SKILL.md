# 中文机关文稿起草

在不补造事实的前提下，依据适用规则形成准确、简洁、可复核的中文机关文稿。

## 规则准入

1. 起草前读取相对于本 Skill 目录的 `../../standards/sources/coverage.yaml`。
2. 正式成稿只能把 `active` 规则作为确定性规范依据。
3. 开发测试时可以使用 `source_checked` 或 `human_approved` 规则，但必须声明其尚未转为 `active`，不得把结果表述为正式规范审核结论。
4. 不使用 `extracted`、来源不明或已失效规则。
5. 不凭模型常识猜测公务员材料规范；现有规范不足时，列出缺少的权威文件并请求用户提供。

## 任务信息

尽量确认：

- 写作目的和期望文种；
- 发文机关、受文机关及隶属关系；
- 事项是否属于发文机关职权；
- 必须写入的事实、时间、数据、政策依据和附件；
- 需要请求、部署、周知或汇报的具体内容；
- 篇幅、语气、交付格式和内部特殊要求。

缺少信息但仍可安全推进时，使用明确占位符并附待补清单。缺少信息会改变文种、行文关系或请求事项时，先请用户补充，不擅自决定。

## 起草方式

按 [起草工作流](references/drafting-workflow.md) 执行。选择通知、报告或请示时读取 [文种选择](references/document-types.md)。事实和占位符处理遵守 [事实安全](references/fact-safety.md)。

需要成稿骨架时可使用：

- [通知模板](assets/notice-template.md)
- [报告模板](assets/report-template.md)
- [请示模板](assets/request-template.md)

模板只提供结构，不得覆盖适用规则或用户真实业务要求。

## 成稿要求

- 正文使用简体中文；依法应保留的名称、缩写、型号和外文除外。
- 内容与用户提供的事实一致，不新增未经确认的政策、文号、数据、资金、决定、成果或领导意见。
- 文种、行文方向、主送机关和请求方式相互一致。
- 请示一文一事，报告不夹带请示事项。
- 结构清晰、主题突出、表述准确、文字精练，措施具有可操作性。
- 不把一般工作材料强行套成法定公文。

## 交付

先交付成稿；其后仅列真正需要用户处理的内容：

- 待补信息；
- 待核实事实；
- 需要机关内部确认的职权、授权、会签或口径；
- 使用的关键规则编号。

不得声称文稿已经通过机关内部审核、审批或签发。
