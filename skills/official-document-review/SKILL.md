# 中文机关文稿审核

根据用户提供的文稿、机关关系和业务背景，输出可追溯、分级且可执行的审核意见。

## 规则准入

1. 优先读取相对于本 Skill 目录的 `../../standards/sources/coverage.yaml`。
2. 正式审核只能将 `active` 规则作为确定性规范结论。
3. 开发测试时可以使用 `source_checked` 或 `human_approved` 规则，但必须在结果开头声明“规则尚未转为 active，不得替代正式审核”。
4. `extracted`、来源不明或已失效规则不得作为结论依据。
5. 不根据模型常识补造公文规范。缺少适用规范时，指出缺口并请求用户提供权威材料。

## 开始审核前

确认或识别：

- 文稿全文和用户希望审核的范围；
- 发文机关、主送机关、抄送机关及其隶属关系；
- 行文目的、拟用文种和事项所属职权；
- 文稿所依据的政策、文件、数据和事实；
- 是否存在涉密、内部敏感或个人信息。

缺少组织关系、职权或真实业务背景时，不作武断判断，将相关结论标记为“需补充背景”。不得要求用户上传涉密材料。

## 审核方式

按 [审核工作流](references/review-workflow.md) 执行。需要判定通知、报告或请示时，读取 [文种与行文检查](references/document-types-and-routing.md)。需要输出结果时，使用 [审核报告模板](assets/review-report-template.md)。

审核至少覆盖：

1. 文种是否符合行文目的；
2. 行文关系、主送和抄送是否合规；
3. 是否存在请示一文多事、报告夹带请示等问题；
4. 标题、正文、附件、署名、日期等组成和格式；
5. 标点和数字用法；
6. 政策、文件、数据、时间、人名、地名等事实是否有依据；
7. 内容是否完整、准确、简洁、可执行；
8. 哪些问题必须由机关内部人员确认。

## 输出要求

- 先给总体结论，再列问题。
- 问题分为：`阻断`、`重要`、`一般`、`提示`。
- 每个问题说明位置、问题、依据、修改建议和所需背景。
- 区分“违反明确规则”“需要结合背景判断”“表达优化建议”。
- 引用规则编号和来源位置，不大段复制规范原文。
- 未发现问题不等于已经通过机关内部审核、审批或签发。
